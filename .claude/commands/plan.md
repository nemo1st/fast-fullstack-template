## タスク

以下の手順で設計ドキュメントを作成してください。

1. **設計対象の確認**: `$ARGUMENTS` の内容を確認し、設計すべきスコープを把握する。不明確な場合はユーザーに確認を取る。

2. **目的（Why）の明確化**: この設計・実装が必要な理由を明確にする。以下のいずれかの形式で言語化する：
   - 「（対象者）が（困っている状態）を解消するため」
   - 「（対象者）が（嬉しい状態）になるため」

   目的が明確でない場合は必ずユーザーに質問して確認を取る。設計ドキュメントの冒頭に「目的」セクションとして記載する。

3. **関連コード・ドキュメントの調査**: 設計に必要な既存コード・ドキュメントを読み込み、現状を理解する。最低限以下は参照する。
   - [CLAUDE.md](CLAUDE.md): プロジェクト全体のガイドライン（ブランチ戦略・コミット規約・禁止事項・注意領域）
   - `docs/tasks/`: 既存の設計ドキュメント（存在すれば書式・粒度の参考にする）
   - [infra/README.md](infra/README.md): デプロイ・インフラ構成（Lambda + S3 + CloudFront）
   - 設計対象に関連するコード:
     - Backend (FastAPI): `api/app/`
     - Frontend: `frontend/`
     - Infra (SAM/CloudFormation): `infra/`
   - 特に CLAUDE.md の「注意が必要」な領域（DB設計・スキーマ変更、認証・認可ロジック、外部API連携）に該当する場合は、設計ドキュメント内でその旨と影響範囲を明記する

4. **ファイル作成**: 設計ドキュメントを作成する。
   - 保存場所: `docs/tasks/`（存在しなければ新規作成）
   - ファイル名: `YYYYMMDD_HHMM_{日本語の作業内容}.md`
   - 日時は `TZ=Asia/Tokyo date +%Y%m%d_%H%M` で取得する
   - 例: `docs/tasks/20260826_1430_ユーザープロフィール編集機能.md`

5. **DB migration 要否の明記**: DB 設計・スキーマ変更（テーブル・カラム・インデックス等の追加・削除・変更のいずれか）を伴う場合、設計ドキュメントに「マイグレーション」セクションを設け、対象・操作種別（add / drop / alter）を明記したうえで「migration PR は別で作成し、上長レビューを経ること」と記載する（CLAUDE.md の禁止事項参照）。DB 要素の変更を伴わない場合は migration セクション自体を設けない。

6. **整合性チェック**: 作成したドキュメントが [CLAUDE.md](CLAUDE.md) のガイドライン（ブランチ戦略・禁止事項・注意が必要な領域）と矛盾していないか確認し、矛盾があれば修正する。

7. **完了報告**: 作成した設計ドキュメントのパスを報告し、ユーザーのレビューを待つ。**そのまま実装に進んではならない。**

8. **コミット・PR作成**: ユーザーから OK が出たら、以下の手順で進める。このプロジェクトは `develop` を base とした PR 経由でのマージを前提とする。
   - 現在のブランチを確認する
   - **`develop` / `main` ブランチの場合**: 「`docs/` 用のブランチを切る必要があります。ブランチ名を提案してよいですか？」とユーザーに確認し、`docs/` プレフィックスでブランチを作成してから commit する（`git switch -c docs/<内容> origin/develop`）
   - **作業ブランチの場合**: そのままコミットする
   - コミットメッセージは [CLAUDE.md](CLAUDE.md) の「コミットメッセージ」規約に従う（簡潔・冗長禁止・AI署名禁止）
   - push 後、`gh pr create --base develop` で PR を作成し、PR URL をユーザーに返す（PR 作成は明示的な指示がある場合のみ）

## 注意事項

設計ドキュメントには以下の内容を含めないこと：

- **具体的な実装コード**: 設計書はアーキテクチャや仕様を記述するものであり、実装コードは含めない（特殊なハック実装についての短いコード片は可）
- **今後の展望**: ユーザーが明示的に言及していない将来的な拡張や改善案は記載しない
- **工数見積・所要期間**: 「〇日かかる」「工数は〇人日」などの時間的な見積もりは記載しない
